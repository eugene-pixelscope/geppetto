# 중앙 제페토와 Kubernetes Agent

상태: 중앙 등록·Agent 인증/승인·읽기 전용 노드/PVC 발견·heartbeat·고래 등록을 구현했다.
실제 클러스터 배포와 Agent 기반 작업 실행/원격 파일 접근은 미수행이다.
설치·운영·검증 범위는 [Agent 운영 문서](AGENT_OPERATIONS.md)를 따른다.

## 구성

- **Geppetto Server**: 중앙 UI/API, 사용자 접근, 클러스터 연결 등록, 노드 목록, 피노키오/데이터 카탈로그,
  작업 요청·예약·평가 기록을 보관한다. 여러 Kubernetes 클러스터를 연결할 수 있다.
- **Geppetto Agent**: 연결 대상 클러스터 안에서 실행한다. Kubernetes API로 노드/자원/작업 상태를 관측하고
  중앙의 승인된 작업 의도를 실행 경로에 전달한다. 이름을 등록하는 것만으로 실행 권한이 생기지 않는다.
- **고래**: 실제 Kubernetes Node. cluster_id + Node UID로 식별한다. nodeName은 표시/스케줄링에 사용한다.
  같은 이름의 노드가 재생성되어 UID가 바뀌면 이전 고래의 실행 이력을 덮어쓰지 않는다.
- **피노키오**: 지속적인 모델 정체성. 학습·평가 작업이 연결된다. 모델 템플릿 및 결과 버전과 구분한다.
- **학습·평가 작업**: 지정 고래에서 실행되는 Kubernetes Job/Pod와 중앙 작업 ID를 연결한다.

연결 등록은 클러스터/Agent 단위, 화면에서 관리하는 고래는 노드 단위다.
첫 구현은 클러스터당 Agent Deployment 한 개로 시작한다. 노드마다 Agent를 필수 설치하지 않는다.
로컬 디스크 탐색이나 노드별 GPU 수집처럼 필요한 기능은 별도의 선택적 DaemonSet으로 확장한다.

## 사용자 흐름

1. 중앙에서 ‘Kubernetes 연결 추가’: 표시 이름과 연결 정책을 생성한다.
2. 해당 클러스터용 등록 자격 증명과 Agent 설치 manifest를 제공한다.
3. 관리자가 대상 클러스터에 Agent를 배포한다.
4. Agent가 중앙에 자신과 클러스터 정보를 등록한다. 중앙에서 승인된 연결만 활성화한다.
5. Agent가 발견한 노드 후보를 표시한다. 사용할 학습 노드를 선택하면 고래로 관리한다.
6. 고래 안에서 접근 가능한 데이터/PVC와 모델 템플릿을 확인하고 피노키오를 만든다.
7. 작업 요청에는 대상 cluster_id/Node UID 및 스케줄링 제약이 고정된다.

홈 ‘고래 등록’은 장기적으로 문자열 등록이 아니라 ‘클러스터 연결 → 발견된 학습 노드 선택’ 흐름으로 바꾼다.
현재 1번 고래는 실제 발견한 Node가 아닌 로컬 작업 공간이므로 신규 연결 시 자동으로 실제 노드로 승격하지 않는다.

## 연결·상태

Agent가 중앙 HTTPS endpoint로 나가는 통신을 기본으로 한다. 중앙이 각 노드의 관리 포트를 직접 열 필요가 없다.
등록 자격 증명은 클러스터별로 분리하고, 최초 등록용 토큰과 지속 인증을 분리한다.
토큰 만료/폐기·재발급과 인증서 검증을 지원한다. Kubernetes ServiceAccount 자격 증명은 클러스터 안에 둔다.

구분해서 저장/표시할 상태:
- Agent 연결: 등록 대기 / 연결됨 / 갱신 지연 / 연결 끊김.
- Node: Ready 조건, unschedulable 여부, 마지막 관측 시각.
- 자원: capacity/allocatable/요청량과 실제 사용률을 구분한다. GPU/메모리 사용률은 수집기가 없으면 미기록이다.
- 작업: 제출/대기/실행/완료/실패/중단 및 해당 Pod UID.

Agent 연결이 끊겨도 학습이 실패했다고 단정하거나 Job을 다시 만들지 않는다. 마지막 관측값과 지연을 표시한다.
작업은 브라우저와 중앙 연결의 일시 중단에 독립적으로 계속 실행될 수 있다.

## 실행 소유권과 기존 어댑터

기존 Airflow/Kubernetes 어댑터와 새 Agent가 같은 작업을 동시에 제출해서는 안 된다.
실행 경로를 명시적으로 선택하고 단계적으로 전환한다.

- 현재 경로: 중앙 worker → 전용 Airflow DAG → Kubernetes Pod. 기존 계약은 유지한다.
- Agent 경로(구현 대상): 중앙의 영속 작업 의도 → 클러스터 Agent → 지정 namespace의 Job.
  Agent가 작업 ID로 reconcile하고 같은 요청을 재수신해도 중복 Job을 만들지 않는다.
- 중단은 중앙 작업 ID label과 Job/Pod UID를 대조한 뒤 처리하고 종료 관측을 반환한다.
- 학습 이미지/모델/데이터 버전 allowlist와 최종 확인 hash를 유지한다.
- 선택한 고래에는 node affinity와 GPU requests/limits를 적용하고, 다른 노드로 몰래 대체하지 않는다.
- RBAC는 필요한 노드 읽기와 지정 namespace의 관리 대상 작업에 한정한다. 클러스터 전체 관리자 권한을 기본 요구하지 않는다.

## 데이터 위치

화면상 데이터가 고래 안에 있다는 것은 ‘그 노드에서 학습에 사용할 수 있는 자원’이라는 뜻이다.
PVC/공유 스토리지의 데이터는 여러 고래에서 사용할 수 있으므로, 향후 단일 node_id 소유만으로 제한하지 않는다.
중앙이 원격 노드의 경로를 자기 로컬 파일 경로로 열어서는 안 된다.
Agent의 허용된 volume/PVC 접근과 dataset_id/version을 통해 탐색·검증·미리보기를 제공한다.

## 구현 순서와 검증

1. 연결/Agent/실제 Node를 구분하는 영속 모델과 인증 계약.
2. 읽기 전용 Agent와 노드 발견·heartbeat·연결 지연 UI.
3. PVC/데이터 가용성 및 미리보기 전달.
4. 하나의 실행 경로를 정한 Job 제출·상태 reconcile·중단·로그·결과 연동.
5. 격리된 Kubernetes 환경에서 재시작·중복 요청·연결 단절·노드 교체 검증.

이 문서 작성으로 운영 클러스터 배포, RBAC 변경, Agent 설치 또는 학습 실행을 수행하지 않는다.
